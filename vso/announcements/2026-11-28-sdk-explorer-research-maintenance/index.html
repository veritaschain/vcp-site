VSO · 2026-11-28 · SDK, EXPLORER & RESEARCH MAINTENANCE

VSO updates SDK guidance, the public Explorer and research maintenance records

This 28 November update covers 11 merged pull requests across six repositories and a separate, unmerged Receipt-context experiment. We update the public Explorer GUI from the stated source revision; the separately hosted API is not redeployed by this publication.

Experimental extensions and proposed repairs remain unadopted; independent third-party reproduction has not been established. First-party CI, publication of a GUI bundle and independent reproduction are different results. Fixed distributions, signed data and historical test records are retained.

1. VeraSnap Verify SDK: qualify the insurance-routing example

VeraSnap Verify SDK #8 is merged at 8271efcf4b3eee0c633435ab789e1ed14c176205. The example no longer treats a green result alone as grounds for fast-track review. It also requires media_verified, a passed signer_key check with code known, and an account_ref matching the expected account obtained from the insurer’s authenticated claim record.

Green can coexist with a skipped photo check or a manually registered, unattested key. The example’s routing conditions are not an insurance payout decision or proof that the photographed scene is true. Missing proof, photo or trust files now produce CLI input-error exit code 3. Merkle inclusion checks one event against a supplied root; unsigned deletion-count hints do not establish complete capture history.

The upstream installation instructions pin development revision 1f1289ef21fea84393d42a36ee10152c25cae70e. The new main CI records 196 tests per Python version. The fixed v0.1.0 release’s 125-test record and the later 186-test record remain separate historical results; the fixed release does not include this update. See the version and known-issue matrix.

2. VCP SDK: retain optional policy identification without expanding signature coverage

VCP SDK #26, main 1e75820e954eda7232bc57eb21037efaa1cbf1ba, preserves the optional top-level PolicyIdentification object when vcp seal writes an event. Before signing, the CLI checks that the object’s PolicyID matches Header.PolicyID.

Preserving the object does not make it signed metadata. The event signature covers the hash of Header, Payload and the optional previous hash. The policy block’s conformance tier and registration details remain unsigned. No registration, certification or policy-content authenticity follows from copying this block.

The installation guide points to development revision 59860c5d3180ac8bdc2e8b9df500af7ae2c162f7. Package metadata still says 0.1.0; use the commit SHA to distinguish it from the unchanged v0.1.0 tag at cc6c468. The earlier seal-recovery record at 28d46e8 is retained. Staging two outputs still does not make their replacements one atomic transaction.

3. Public Explorer GUI: preserve displayed precision and label the source of a verdict

The public Explorer GUI is updated from 3627b075dcb0aadf42f01794edb1d3f77ef3f120. #45 retains the fractional seconds supplied in an ISO timestamp when displaying UTC, including date changes caused by an offset. It labels VERIFIED as Verified (API-reported) and shows missing or unknown states as Unknown, rather than treating them as Pending.

#41 and #44 update production and development dependencies. The displayed API-reported status is not an independent browser verification of the event. This GUI publication does not establish that its remote API runs the latest API main or that every displayed record is authenticated.

4. Explorer API: source fixes, with runtime deployment kept separate

API main 6004d377ca5f1881857220f1956962c92554e36e includes #44 for consistent nanosecond timestamps across event summaries, details and certificate data; #45 for newest-first recent events and case-insensitive hexadecimal UUID/trace lookups; and #46 for package-version reporting and the published developer-guide link.

The root and health responses now derive the source package version, 1.1.0, instead of the old hard-coded value. This is not a new tagged release. These are repository changes with successful first-party CI. The separately managed API runtime is not deployed by this site update. The existing API and GUI v1.0.0 tags are unchanged.

5. VCP event CLI: distinguish an omitted enumeration from an empty one

VCP specification repository #47, main 03bbfe5f68ec9a81f32108146a3ebe43d0800541, fixes the optional ERASURE Scope.EventIDs check when using a custom schema. If supplied, the array must be nonempty and agree with the count and first/last IDs. Omitting the optional field retains its previous handling. The default schema already requires at least one entry.

Only the local CLI and its regression test change. This is not a normative-text or schema change and does not add cryptographic signature or Receipt verification. Its main CI passed 41 tests; the earlier 40-test record remains available.

6. CAP-SRP: use attempt IDs for local coverage and keep demo sessions together

CAP-SRP #8 replaces a count-only statistics check with the existing attempt-ID matching check. A window containing one orphan outcome and a different pending attempt no longer appears complete merely because the counts match. The pending count is the number of supplied attempts without a matching outcome.

#9 copies the originating attempt’s session ID into CLI and Custom Demo success, refusal and error outcomes. Filtering generated records by session can therefore retain the matching attempt/outcome pairs. Combined main 20b24a4e846c25721b728266bc183bd831bef77b passed 417 full-suite tests; the separate 365-test regression suite is a subset, not an additional 365 distinct tests.

These are local PoC and synthetic-demo corrections. They do not establish that unrecorded requests were captured, that the source set is complete, that an external anchor is authenticated, or that CAP/VAP conformance has been established. No separate hosted CAP-SRP deployment is claimed.

Separate unmerged work: seven Receipt-context cases now have a fixed replay

Draft PR #45 remains open and unmerged at 45c99c2e5b5700ee8d2841b89fa0471b84572ecc. Its fixed replay package now covers seven of the 22 proposed cases. Two first-party implementations, Python and Go, each make eight assessments: five verify inclusion under the declared, authorized service context, two lack applicable key authorization, and one has ambiguous rule context. The compared reports agree on every field.

The fixture reuses two synthetic Receipts for a two-leaf tree and the restricted A1 entry construction. Fifteen cases remain unexecuted. Source completeness, history consistency, issuance time, position/size and local VCP batch integrity remain unassessed. Both implementations originate from this experiment; their agreement is not external independent reproduction or full SCITT-VCP profile interoperability.

The 27 November notice is preserved as the prior check record, including its earlier “zero executed cases” statement. This dated notice records the newer branch state. It does not move the draft into main, adopt its proposed requirements or change the published -07 baseline.
