VeraSnap Verify SDK 0.1.0を公開 — CPPの撮影証明をサーバー側で検証するオープンソースSDK

2026年11月18日、VSOを運営するVeritasChain株式会社は、VeraSnap Verify SDK 0.1.0をApache License 2.0でGitHubに公開しました。証拠として写真を受け取る組織が、自社のサーバーで、写真に有効なVeraSnapの撮影証明が付いているか、その証明が自社で登録した端末鍵で署名されているかを確かめるためのものです。最初の利用者として想定しているのは、保険金請求の写真を扱う損害保険会社です。

VSOの運営会社による自社実装のアルファ版です。第三者による監査は受けておらず、CPPの適合性テストスイートでも認証でもありません。テストは自社のCIでのみ実行しています。証明が示すのは、いつ・どの端末で撮影が記録されたかと、それ以降にファイルが変わっていないことです。写真の内容が真実であることは示しません。CPPの外部実装や、証拠として採用された証明があるとは主張していません。

1. 公開したもの

リポジトリには、Pythonのパッケージ（Python 3.10以降）、コマンドラインツール、英語と日本語のドキュメントが含まれます。検証時にネットワークは使いません。VeraSnapアプリが書き出す3つの形式（共有用の証明JSON、内部形式のproof.json、Evidence PackのZIP）を受け付けます。

証明ごとに行うチェック
チェック確かめること
メディアのハッシュとES256署名ファイルが、端末で署名されたイベントと一致すること。
RFC 3161タイムスタンプトークンがこの証明のアンカー済みダイジェストに対して発行されたこと。CMS署名、ESSCertID、拡張鍵用途、genTime時点の証明書チェーンを同梱のルート証明書で検証し、検証できた時刻だけを返します。
端末鍵の登録鍵の登録時に、Android Key AttestationとApple App Attestを検証します。緑になるのは、受け取る組織が登録した鍵で署名された証明だけです。
撮影時刻とタイムスタンプの整合記録上の撮影時刻からタイムスタンプまで60分を超えると警告になります。VeraSnap 1.6.1アプリと同じ基準です。撮影時刻そのものは端末の時計の値です。
Merkleへの包含イベントがアンカー済みのバッチに含まれていること。チェーンコンテキストの削除件数は署名の対象外のため、参考値として示します。

結果は緑（ANCHOR_VERIFIED）、黄（PARTIALLY_VERIFIED・ANCHOR_PENDING）、赤（SIGNATURE_INVALID・HASH_MISMATCH・ERROR）のいずれかで、各チェックは固定のコードで一覧になります。

2. 背景：保険金請求写真の事後チェック

公表されている情報

2026年には国内の損害保険会社で、提出された画像を事後に分析し、生成AIの痕跡や使い回しを検知する仕組みの導入が始まりました。三井住友海上・あいおいニッセイ同和損保 2026年8月3日発表（PDF） · 東京海上日動 2026年9月30日発表（PDF）

VSOの分析 — 実証された結果ではありません

事後の検知はすべての写真に適用できますが、結果は確からしさであり、画像生成AIの進化を追い続ける必要があります。撮影証明は一致か不一致かを示せますが、対象は撮影時に封印するカメラで撮った写真に限られます。そのためこのSDKは、既存の検知を置き換えるものではなく、その前段に置く層として説明しています。不正の減少は測定していません。

3. 不正の手口と結果

  • 撮影後の加工・AIによるインペインティング、再圧縮、ファイルの差し替え：赤。ハッシュが署名と一致しなくなります。
  • 攻撃者自身の鍵と本物のタイムスタンプで作った偽の証明：黄。鍵が登録されていないため、緑にはなりません。
  • 撮影時刻のさかのぼり：黄。タイムスタンプが記録上の撮影時刻から60分より後になります。
  • タイムスタンプの付け替え・削除、証明の書き換え：赤。
  • 後から付けた傷や別の車両を本物のカメラで撮る：検知しません。偽りの場面を本物のカメラで撮った写真は、検証に通ります。
  • 画面に表示した画像の再撮影：判定しません。アプリは画面検知の結果を参考値として記録しますが、SDKでは使っていません。

4. CPPおよびVeraSnapアプリとの関係

このSDKは、VeraSnap iOSアプリ1.6の検証ロジックと1.6.1の規則（署名鍵の出所、撮影時刻の整合、検証済みトークンからだけ取るタイムスタンプ時刻）を移植したものです。再現しているのはアプリの形式であり、draft-vso-cpp-coreではありません。たとえばMerkle木は、リーフとノードのドメイン分離のない、アプリと同じ構成です。

証明の中に書かれた端末の証明情報は「記載あり・未検証」として扱います。撮影ごとのApp AttestとPlay Integrityの検証は、CPP v1.7 Capture Environment Attestationの草案に属し、実装していません。アプリとの意図的な違い（たとえば、未登録の署名鍵は受け取る組織が登録しない限り黄になる）は限界と未対応事項に記載しています。

5. テストとその範囲

125件のテストを、自社のCIでPython 3.10・3.12・3.13について実行しています。公的なタイムスタンプ局から取得したRFC 3161トークンを使う不正シナリオ31件、Googleが公開しているAndroidの鍵証明チェーン、合成したApp Attestのデータ、正規化とMerkleのケースを含みます。1つのシナリオはOpenSSLでも照合しました。正規化は、VeraSnap iOSのテストに含まれるフィクスチャのEventHashを再現します。

まだ行っていないこと：現行アプリを搭載した端末から書き出した証明の検証、アプリ自身のシナリオテストとの突き合わせ、第三者による独立した再現、セキュリティ監査。

6. 撮影SDK

保険会社のアプリに組み込む撮影SDK（iOSのSwift PackageとAndroidのAAR）は設計段階で、設計はリポジトリで公開しています。オープンソースではなく、今回の公開には含まれません。
