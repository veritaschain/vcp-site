VeraSnap Verify SDK 0.1.0 发布：在服务器端验证CPP拍摄证明的开源SDK

2026年11月18日，运营VSO的VeritasChain株式会社在GitHub上以Apache License 2.0发布了VeraSnap Verify SDK 0.1.0。接收照片作为证据的组织可在自己的服务器上确认：照片是否附有有效的VeraSnap拍摄证明，以及该证明是否由本组织登记的设备密钥签名。首批预期用户是处理理赔照片的财产保险公司。

这是VSO运营方自行实现的Alpha版本，未经独立审计，既不是CPP符合性测试套件，也不是认证。测试仅在自有CI中运行。证明显示的是拍摄在何时、由哪台设备记录，以及此后文件未被更改；它不能证明照片内容属实。本公告不主张存在CPP的外部实现，也不主张有证明在任何程序中被采纳。

1. 发布内容

代码库包含Python软件包（Python 3.10及以上）、命令行工具以及英文和日文文档。验证时无需网络连接。它接受VeraSnap应用写出的三种格式：可共享的证明JSON、内部格式proof.json以及Evidence Pack ZIP。

对每份证明执行的检查
检查确认的内容
媒体哈希与ES256签名文件与设备上签名的事件一致。
RFC 3161时间戳令牌是针对本证明已锚定的摘要签发的。使用内置根证书验证CMS签名、ESSCertID、扩展密钥用法及genTime时点的证书链，仅报告经验证的时间。
设备密钥登记登记密钥时验证Android Key Attestation和Apple App Attest。只有接收方组织登记的密钥才能得到绿色结果。
拍摄时间与时间戳记录的拍摄时间与时间戳相隔超过60分钟时给出警告，与VeraSnap 1.6.1应用的规则相同。拍摄时间本身是设备时钟的值。
Merkle包含事件包含在已锚定的批次中。链上下文中的删除计数不在签名范围内，仅作为提示显示。

结果为绿色（ANCHOR_VERIFIED）、黄色（PARTIALLY_VERIFIED、ANCHOR_PENDING）或红色（SIGNATURE_INVALID、HASH_MISMATCH、ERROR），每项检查都以固定代码列出。

VSO分析——并非已证实的结果

事后检测可应用于所有照片，但给出的是可能性，并且必须跟上图像生成技术的发展。拍摄证明给出的是一致或不一致，但仅适用于用会在拍摄时封存照片的相机拍摄的照片。因此，本SDK被定位为置于现有检测之前的一层，而非替代。尚未测量欺诈是否减少。

3. 欺诈手法与结果

  • 拍摄后编辑或AI修补、重新压缩或替换文件：红色，因为哈希不再与签名一致。
  • 使用攻击者自己的密钥和真实时间戳伪造的证明：黄色，因密钥未登记，永远不会是绿色。
  • 倒填拍摄时间：黄色，因为时间戳比记录的拍摄时间晚60分钟以上。
  • 替换或删除时间戳、修改证明：红色。
  • 用真实相机拍摄人为制造的损伤或其他车辆：无法检测。对虚假场景的真实拍摄可以通过验证。
  • 翻拍屏幕上显示的图像：不作判断。应用会将屏幕检测结果作为提示记录，但SDK不使用这些结果。

4. 与CPP及VeraSnap应用的关系

本SDK移植了VeraSnap iOS应用1.6的验证逻辑及1.6.1的规则（签名密钥来源、拍摄时间一致性、仅从经验证的令牌获取时间戳时间）。它复现的是应用的格式，而非draft-vso-cpp-core；例如，Merkle树采用与应用相同、没有叶节点与内部节点域分离的构造。

证明中写入的设备证明信息按“已声明、未验证”处理。每次拍摄的App Attest与Play Integrity验证属于CPP v1.7 Capture Environment Attestation草案，尚未实现。与应用的有意差异（例如，未登记的签名密钥除非由接收方组织登记，否则为黄色）列于限制说明中（英文）。

5. 测试及其范围

125项测试在自有CI中于Python 3.10、3.12和3.13上运行，涵盖使用公共时间戳机构RFC 3161令牌的31个欺诈场景、Google公开的Android密钥证明链样本、合成的App Attest数据，以及规范化和Merkle用例。其中一个场景还使用OpenSSL进行了交叉核对。规范化可复现VeraSnap iOS测试中夹具的EventHash值。

尚未完成：从运行当前应用的设备导出的证明的验证、与应用自身场景测试的对照、独立的第三方复现以及安全审计。

6. 拍摄SDK

用于保险公司自有应用的拍摄SDK（iOS Swift Package和Android AAR）处于设计阶段，设计已在代码库中公开。它不是开源软件，也不包含在本次发布中。
