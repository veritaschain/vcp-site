この手順で確認すること

公開済みの合成データ7ケースを既存のVeraSnap Verify SDKで検証し、各ケースのJSON全文・標準エラー・終了コードを保存します。写真の証跡を受領側で確認するSDKであり、取引ログ向けのVCP SDKとは別です。撮影アプリ、受領側のVerify SDK、設計段階のCapture SDKも区別します。

自社開発のalpha版です。 この手順は、本番適合、法令適合、保険での受理、独立したセキュリティ監査、VAP／CPPへの完全適合、第三者による独立再現の成立を示しません。実験的拡張・修正案は未採択のままです。

試験入力は合成メディアのバイト列と公開試験鍵です。顧客の実写真や、実際の保険事故の証拠ではありません。2026年11月18日に取得して保存された実際のRFC 3161トークンをオフラインで再検証します。新しいタイムスタンプを要求するtools/make_fixtures.pyは実行しません。固定した入力一覧を参照してください。

パッケージ番号だけでなく、ソースの版を固定する

このガイドは2026年11月26日に確認したmainのスナップショット66d1875b5977feacb755c3bb92c38d2f2ba39665を固定します。リリース後の鍵の再登録・Android鍵証明パスの修正を含みます。READMEの推奨導入版は先行する実装コミット4eaa3b73e049bf14dbff0dcea30cf18c627ee617で、今回のmainにはその後の文書修正も含まれています。

過去のv0.1.0 alphaリリースは0caa054b074b09524045b8ee948f63d450b5b7dbを指し、自社試験125件の記録を保持しています。READMEは後続の固定実装で自社CI186件の成功を記録しています。どちらもパッケージの版表示は0.1.0なので、それだけでは実際のコードを識別できません。このガイドでタグ・固定ZIPを差し替えたり、過去の結果を更新したりはしません。

1. 新しいディレクトリと仮想環境を用意する

Git、Python 3.10以降、macOS／LinuxのBash、またはWSLなどの互換シェルを使います。このページの手順を実行確認した環境はmacOS・Python 3.14.3と下記の依存バージョンです。他の環境を今回すべて再実行したわけではありません。取得・パッケージのインストールには通信が必要ですが、後の7ケースはローカル入力とSDK同梱のTSAルート証明書を使います。

verasnap-sdk-guideがまだ存在しない場所から実行してください。本番用の鍵台帳・秘密鍵・顧客の証拠は使いません。

git clone https://github.com/veritaschain/verasnap-verify-sdk.git verasnap-sdk-guide
cd verasnap-sdk-guide
git checkout --detach 66d1875b5977feacb755c3bb92c38d2f2ba39665
git rev-parse HEAD
python3 -m venv .venv
. .venv/bin/activate
python -m pip install "cryptography==50.0.2" "asn1crypto==1.5.1" "cbor2==6.3.0" .
verasnap-verify --version

git rev-parse HEADが66d1875b5977feacb755c3bb92c38d2f2ba39665を返すことを確認します。版表示はverasnap-verify 0.1.0ですが、コミットも残してください。以降は同じディレクトリ・有効化した仮想環境で続けます。

2. 環境と入力のハッシュを記録する

新しいguide-outputディレクトリを作り、ソースのコミット、依存バージョン、入力のSHA-256を記録します。すでにこのディレクトリがある場合は前回分として保持し、新しいクローンで開始してください。実行証拠を黙って上書きしません。

mkdir guide-output
python - <<'PY'
from pathlib import Path
import hashlib, importlib.metadata, json, platform, subprocess
source = Path('tests/fixtures/scenarios')
files = [source/'manifest.json'] + sorted(source.rglob('proof.json')) + [source/'S28/proof.zip', source/'media/photo.jpg', source/'media/photo_edited.jpg']
record = {
    'commit': subprocess.check_output(['git', 'rev-parse', 'HEAD'], text=True).strip(),
    'python': platform.python_version(),
    'platform': platform.platform(),
    'dependencies': {p: importlib.metadata.version(p) for p in ('verasnap-verify', 'cryptography', 'asn1crypto', 'cbor2')},
    'input_sha256': {str(p): hashlib.sha256(p.read_bytes()).hexdigest() for p in files},
}
Path('guide-output/environment-and-inputs.json').write_text(json.dumps(record, indent=2)+'\n')
PY

インストールされた依存関係の一覧も保存します。

python -m pip freeze > guide-output/pip-freeze.txt

これは今回使ったバイト列を特定する記録です。実行ホストの真正性や、独立再現の成立を証明するものではありません。

3. この演習に限って公開試験鍵を登録する

ソースの既存試験は、公開された試験鍵を手動登録して使っています。以下で同じ設定を作ります。これはAndroid Key AttestationやApple App Attestによる端末鍵登録ではありません。判定の扱いを試すためのローカルな信頼設定です。

trial_key=$(python - <<'PY'
import json
from pathlib import Path
print(json.loads(Path('tests/fixtures/scenarios/manifest.json').read_text())['keys']['device_enrolled'])
PY
)
verasnap-verify keys --registry guide-output/test-keys.sqlite add \
  --public-key "$trial_key" --account fixture-only \
  --note 'Public synthetic fixture; manual registration, not device attestation' \
  > guide-output/test-key-fingerprint.txt
unset trial_key

この鍵のsigner_keyはpassed / known_unattestedとなり、ハードウェア証明で登録したknownとは異なります。緑にするために、顧客が送った証明の鍵をそのまま登録しないでください。本番の登録には、別の認証手順、チャレンジとアカウントの結び付け、鍵台帳・失効管理が必要です。鍵登録の資料を確認してください。公開されている試験用秘密鍵を、実際の署名に流用してはいけません。

4. 7ケースを実行し、非ゼロ終了も保存する

以下は既存CLIを呼び出します。シェル関数は出力と終了コードを保存するだけで、新しい検証器ではありません。期待する黄・赤の判定を、シェルの成功終了に読み替えません。--allow-unknown-signerや信頼条件の緩和は使いません。入力原本は読み取るだけで編集しません。

run_case() {
  case_name=$1
  shift
  if verasnap-verify verify "$@" --json \
    > "guide-output/$case_name.json" 2> "guide-output/$case_name.stderr.txt"; then
    case_exit=0
  else
    case_exit=$?
  fi
  printf '%s\n' "$case_exit" > "guide-output/$case_name.exit.txt"
}
fixtures=tests/fixtures/scenarios
run_case S01 "$fixtures/S01/proof.json" --media "$fixtures/media/photo.jpg" --registry guide-output/test-keys.sqlite
run_case S02 "$fixtures/S02/proof.json" --media "$fixtures/media/photo.jpg"
run_case S03 "$fixtures/S03/proof.json" --media "$fixtures/media/photo_edited.jpg" --registry guide-output/test-keys.sqlite
run_case S27 "$fixtures/S27/proof.json" --media "$fixtures/media/photo.jpg" --registry guide-output/test-keys.sqlite
run_case S13 "$fixtures/S13/proof.json" --media "$fixtures/media/photo.jpg" --registry guide-output/test-keys.sqlite
run_case S20 "$fixtures/S20/proof.json" --registry guide-output/test-keys.sqlite
run_case S28 "$fixtures/S28/proof.zip" --registry guide-output/test-keys.sqlite

S01は基準ケース、S02は鍵台帳なし、S03はメディアを1ビット変更したケースです。S27は内部形式のTSAトークン不足、S13は共有形式のタイムスタンプ欄削除です。S20はメディア未提出、S28はメディアと証跡を含むEvidence Pack ZIPを使います。意図的に異なる判定を確認します。

5. 期待結果と、項目別の判定を照合する

python - <<'PY'
from pathlib import Path
import json
for name in ('S01', 'S02', 'S03', 'S27', 'S13', 'S20', 'S28'):
    result = json.loads(Path(f'guide-output/{name}.json').read_text())
    code = Path(f'guide-output/{name}.exit.txt').read_text().strip()
    print(name, 'exit='+code, result['level'], result['status'], 'media_verified='+str(result['media_verified']).lower())
PY

今回のローカル実行では、次の要約が得られました。

S01 exit=0 green ANCHOR_VERIFIED media_verified=true
S02 exit=1 yellow PARTIALLY_VERIFIED media_verified=true
S03 exit=2 red HASH_MISMATCH media_verified=false
S27 exit=1 yellow PARTIALLY_VERIFIED media_verified=true
S13 exit=2 red ERROR media_verified=true
S20 exit=0 green ANCHOR_VERIFIED media_verified=false
S28 exit=0 green ANCHOR_VERIFIED media_verified=true

色だけで受領後の処理を決めないでください。 S20は緑でもmedia_verified=falseです。メディアを渡していないため、media_hashはスキップされています。S01／S28も手動登録した試験鍵を信頼した結果であり、本物の端末や撮影者本人を証明したわけではありません。これらの入力に書かれたattestationはinfo / statedで、SDKが撮影ごとの証明を検証した結果ではありません。

S27とS13の違いは、「タイムスタンプ不足」を一律の色にまとめられない例です。形式と不足した欄により、名前付きの確認項目が変わります。checks[].id/status/code、media_verified、署名鍵の状態、検証できたtimestamp_timeを確認します。緑は、写真の内容が真実であることや、保険金を支払うべきことを示しません。結果フィールドの資料。

結果が異なる場合

調査前にJSON・標準エラー・終了コードのファイルを保持します。このCLIの0／1／2は緑／黄／赤であり、VAP研究用検証器やVCP SDKの終了コードとは別です。CLIは入力エラーを終了コード3と説明していますが、予期しないトレースバックやJSONでない出力が出た場合は、実行上の問題として記録してください。黄の検証結果に読み替えません。

完全なコミット、依存バージョン、入力ハッシュ、鍵台帳のパスを照合します。すでに登録した試験鍵の再登録は、上書きせず拒否されます。新しいクローン・実行ディレクトリでやり直してください。成功に見せるための期待結果の変更、任意の信頼ルート追加、不合格入力の差し替えはしません。環境差分と失敗を残し、必要な点を技術担当へ確認します。

残す記録と、今回の確認範囲

コミット、environment-and-inputs.json、pip-freeze.txt、試験用台帳と鍵のフィンガープリント、各JSON・標準エラー・終了コードを保持します。出力には鍵のフィンガープリント、アカウント参照、端末の申告値が含まれる場合があるため、共有前に確認します。公開用に加工する場合は、原本を残して作業用コピーを使ってください。

2026年11月26日、上記7ケースのCLI結果が公開試験の期待判定と一致し、同じ隔離仮想環境で未変更のSDK試験も186件成功しました。選んだ版と保存済み入力の自社ローカル確認です。新しい第三者タイムスタンプの発行、ハードウェアを使う鍵登録、本番導入、第三者による独立再現を確かめたものではありません。SDKの実装・固定リリース・過去の試験記録は変更していません。

このSDKはTSAのCRL／OCSP失効確認、被写体の真実性、撮影者本人の特定、撮影ごとのattestation検証を行いません。撮影時刻は端末の申告値です。検証できたタイムスタンプが示す証跡と時刻の結び付きを、絶対的な撮影時刻の正しさと同一視しません。Pinned SDK README · Result codes · Limitations。
