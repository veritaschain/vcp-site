写真と証明を受け取る担当者へ

保険会社の受付担当、企業の現場記録担当、技術支援担当が、VeraSnapの写真と撮影証明を受け取った後の確認を揃えるためのガイドです。暗号学的な検証結果と、事故・損害の事実認定や支払い判断は別に記録します。本ページは推奨する受領手順であり、新しい規範要件や保険金支払い基準ではありません。

このページにファイルをアップロードする機能はありません。組織が承認した受領経路と保存先を使用してください。操作する技術担当者はVerify SDK実行ガイド、使用する版は版・配布物・既知問題一覧で確認できます。

対象SDKは自社開発のalpha版です。実験的拡張・修正案は未採択で、第三者による独立再現は未成立です。

1. 原本と受付情報を保存する

  1. 写真・証明・送付時の説明を分けて受領。画像ファイル、対応する共有用証明JSONまたはエクスポートZIP、提出目的と対象を記録します。画像だけの場合は証明を受領済みとはしません。
  2. 原本は加工しない。受領時刻（タイムゾーン付き）、ファイル名、バイト数、SHA-256、受領経路、担当者を保存し、作業用コピーを作ります。画像の圧縮・再保存・スクリーンショット化はハッシュを変えることがあります。
  3. 送付者の説明とファイルの内容を区別。撮影対象・日時・場所・人物の申告を、暗号学的に確認済みの事実に置き換えません。不要な個人情報は作業記録に複製しません。
  4. 検証条件を保存。SDKの完全コミットSHA、依存関係、鍵台帳の識別情報と適用ポリシー、信頼するTSAルート、検証日時を記録します。秘密鍵や認証情報は記録へ添付しません。

受領時のSHA-256は、その後同じバイト列を扱っているかを照合する手掛かりです。送付者の身元や、受領前の履歴を単独で証明するものではありません。

2. 写真を渡し、個別の検証結果を読む

  1. 原本を残したまま、技術担当者が固定したSDK版で作業用コピーを検証します。写真の照合が目的なら、証明だけでなく写真ファイルも入力します。
  2. 終了コード・標準エラーとJSON結果を保存し、status・levelに加えてmedia_verified、checksのid・status・codeを読みます。
  3. 使用した鍵登録経路を確認します。known_unattestedは手動登録です。knownは、渡した台帳上で証明付きとして扱われる有効な登録鍵を示します。検証時に登録時のハードウェア証明を再検証したという意味ではありません。登録手順の証拠と台帳の管理を別途確認します。
  4. 不足項目・不一致・未検証事項を残し、必要な原本や説明を追加で依頼します。評価条件を変える場合は理由と再実行結果を別記録にします。

受領後に証明中の公開鍵を台帳へ追加して「緑にする」運用にはしません。鍵と顧客の対応は、事前に決めた登録・本人認証の手順から確認します。VeraSnap Verify SDK — device key enrollment

この版の署名鍵チェックは、提供された台帳を参照します。VeraSnap Verify SDK — signer-key lookup and check implementation

3. 色と業務判断を切り分ける

VeraSnap Verify SDK main 66d1875の結果の読み方
出力確認すること・次の対応
緑 / ANCHOR_VERIFIED検証対象になったチェックの結果です。写真未入力でも緑になるため、写真の確認にはmedia_verified=trueとmedia_hash/passed/matchを確認します。事故・被写体・撮影者の真正性を保証しません。
黄 / PARTIALLY_VERIFIED警告の理由を個別に確認。未知の鍵、未検証の時刻などを区別します。「偽造確定」でも「必要な項目を全て確認済み」でもありません。
黄 / ANCHOR_PENDING完全に検証されたタイムスタンプがない状態。何が不足しているかを確認し、予定や期待だけで時刻を確定しません。
赤 / HASH_MISMATCH、SIGNATURE_INVALID、ERROR失敗したチェックを保存。別ファイル、再圧縮、形式不備、改変等を切り分けます。技術的な失敗を理由に不正行為を即断せず、対応する原本を再取得して比較します。
skipped / info合格に読み替えません。写真なしのnot_providedや、証明内端末情報のattestation/info/statedを明記します。これらは総合色を変えません。

タイムスタンプの欠落は入力形式によって扱いが異なります。同じ版の合成例では、内部形式のトークン不足は黄、共有形式からタイムスタンプを削除した入力は赤でした。「タイムスタンプなしは常に黄」と決めつけず、checksを確認してください。コードと集約規則：VeraSnap Verify SDK — result reference

4. 証明できる範囲を記録する

  • 写真の一致：入力写真と署名で結び付いたハッシュの一致を確認しても、写った損害が実際の事故によるものか、画面や印刷物の再撮影でないかは別の確認が必要です。
  • 時刻：capture_time_deviceは端末時計の値です。検証されたRFC 3161時刻は対象ダイジェストがその時刻までに存在したことに関する証拠であり、撮影時刻そのものの独立証明ではありません。
  • 人物・場所：生体認証の記録から撮影者の身元は特定できません。GPSも端末の申告です。顧客IDと登録鍵の対応、対象物の同一性は業務側で別途確認します。
  • 履歴：chain_contextの削除件数等は署名対象外の参考情報です。全操作を捕捉した証明には使用しません。
  • 信頼と失効：この版はTSAのCRL/OCSP失効確認を行いません。証明内の端末証明や撮影ごとのアサーションも、記載されているだけで検証済みにはなりません。

VeraSnap Verify SDK — limitations。本ガイドの確認は自社による合成例の実行と公開資料の照合です。独立した第三者による再現・監査・本番適合を示しません。

6. 調査へ引き継ぐ

不一致がある場合は、原本を保持し、再取得したファイルを別の受領物として記録します。結果を揃えるために元証明を書き換えたり、信頼設定を無記録で変更したりしません。

問い合わせには、使用版、入力形式、チェックID・コード、個人情報を除いた再現条件を先に伝えます。顧客写真、鍵台帳、業務用認証情報を公開Issueに投稿しないでください。機密資料が必要な場合は承認された共有経路と範囲を別途決めます。相談・問い合わせ

手順を実行する担当者には実行ガイド、変更版の選択には版・既知問題一覧を引き継いでください。固定配布物は書き換えず、別版での確認を別の実行記録として扱います。
