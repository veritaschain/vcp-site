写真を受け取る業務へ。

写真だけを受け取る流れに、原本と結び付いた撮影記録を加える。まず一つの業務を選び、既存の確認手順と併用する評価を考えます。

保険会社・損害調査

請求写真の確認

写真と証跡の整合性や、登録鍵・時刻の確認結果を、担当者が参照できる材料にします。保険金支払いの判断は既存の審査と分けて扱います。

建設・設備・不動産

現場点検の引き継ぎ

点検写真の原本と対応する証跡を保存し、引き継ぎ後にも確認できる形を検討します。撮影対象や点検内容の正確さは別途確認します。

法務・監査・記録管理

受領後の再確認

誰が何を受け取り、どの版・どの条件で検証したかを残す運用へ。共有権限、保存期間、個人情報の扱いも一緒に設計します。

上記は導入を検討するための用途例です。顧客の採用実績や、損害・不正を防止した実績を示すものではありません。

確認できることを、切り分ける。

証跡が正しくても、写真の内容が正しいとは限りません。検証条件を満たした項目と、別の確認が必要な項目を一緒に表示することが重要です。

確認する項目証跡から確認することそれだけでは分からないこと
ファイルと署名渡された写真が証跡のハッシュと一致し、署名が検証できるか。被写体の真実性、加工以前の状態、撮影の正当性。
タイムスタンプ信頼するTSAの時刻証拠と、対象データとの結び付き。端末が記録した撮影時刻の絶対的な正しさ。
登録された鍵検証した端末鍵の登録記録と、署名鍵が対応するか。撮影者本人の特定や、請求内容・撮影場所の正しさ。
検証の結論対象の版・入力・信頼条件における確認済み／未確認／不一致。法的な証拠採用、保険金支払いの可否、完全適合や独立監査の成立。

上記は受領側で評価する項目です。VeraCheck Webのβビューアが、これらをすべて検証するという意味ではありません。

VeraSnap Verify SDK

写真と証跡を受け取るPython向けSDK。署名・時刻証拠・鍵登録の確認を評価できます。APIは変更される可能性があり、独立監査済みではありません。

SDKの現行案内と制約を見る

鍵の登録は別の準備が必要です。 一般向けアプリで撮影しただけでは、保険会社に端末鍵が登録されたことにはなりません。SDKでは未知の鍵の証跡は、署名とタイムスタンプが正しくても「部分的な検証」に留まります。

企業独自のアプリへ撮影機能を組み込むCapture SDKは設計段階です。公開済みのVerify SDKとは別です。

EVALUATION

一つの業務で、小さく評価する。

本番データを集める前に、対象と成功条件を決めます。結果が不明なケースも、業務でどう扱うかまで確認します。

  1. 対象を決める

    例えば、損害写真の受付一工程。提出する人、受領担当者、現状の確認方法を整理します。

  2. 試験データで一巡する

    合成データや利用権限のある試験写真で、撮影・原本保存・証跡受領・検証を試します。

  3. 失敗と未確認も確認する

    ファイル変更、未知の鍵、時刻証拠不足などを含め、業務判断に使える結果表示かを評価します。

  4. 導入条件を合意する

    利用許諾、データの保存先、閲覧権限、保管期間、費用、支援範囲を個別に確認します。

導入検討でよくある質問

AI生成画像や保険金不正を、自動で判定できますか？

画像の内容が真実か、不正があるかを自動で保証する製品ではありません。署名やハッシュ、時刻証拠、登録鍵の確認結果を、他の調査材料と組み合わせて使います。

既存の保険会社アプリに、そのまま組み込めますか？

受領側のVerify SDKは公開alpha版として評価できます。撮影機能を組み込むCapture SDKは設計段階です。既存アプリへの接続、鍵の登録、運用条件は個別に検討します。

法人での利用条件はどう確認しますか？

公開アプリのEULAには個人・非商業利用に関する記載があります。法人利用の可否・許諾条件は事前に窓口で確認してください。Verify SDKのApache-2.0ライセンスと、アプリの利用許諾は別です。

ブラウザーで証拠パックを開けば、すべて検証できますか？

VeraCheck Webは表示と限定的なチェックを行うβビューアです。Merkle証明やTSA情報の存在表示は、その暗号学的な完全検証とは異なります。検証器の版、対応項目、未確認項目を確認してください。
