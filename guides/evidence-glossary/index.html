1. Matching data and checking signatures

A practical glossary for people reviewing AI records and photo evidence. Examples explain concepts; they introduce no new normative requirements, result codes or insurance acceptance rules. Check signature integrity, evidence fulfillment, permission to act and the business decision separately.

Hash / digest

A value calculated from a sequence of bytes. For example, retain a photo's SHA-256 at receipt and compare it with a later working copy. Different values mean different bytes. A match does not establish the scene's truth or the sender's identity; the reference digest also needs a trustworthy origin.

Canonicalization

A specified way to turn structured data into a representation for hashing or signing. JSON key order or whitespace can differ while a chosen canonicalization rule produces the same bytes. The number 1 and string "1" remain different. This is not permission to guess and rewrite types or units. RFC 8785 §3 — JSON canonicalization

Digital signature

A mechanism for checking a message, signature and public key against the chosen algorithm's rules. Changing a signed receipt's amount, for example, makes it inconsistent with the original signature. Separately establish who controls the key, its validity or revocation, and which fields were signed. A valid signature does not make the recorded claim true. RFC 8032 §5.1.7 — Ed25519 signature verification

2. Time and membership in a collection

Timestamp

An RFC 3161 timestamp authority token binds a digest to a time. With appropriate trust and verification, it provides evidence that the data existed by that time. A timestamp on a photo does not establish when the pictured incident happened. Keep it separate from a device-clock value. RFC 3161 §2.1 — timestamp authority requirements

Merkle inclusion proof

Evidence that an item is bound to a particular tree root, checked using a hash path and the selected construction's size and position rules. Proving one submitted item belongs to a batch does not establish that every real-world action was recorded in the first place. RFC 9162 §2.1.3 — Merkle inclusion proofs

Anchor / external commitment

A reference point binding a record digest or collection root to another store, receipt or time service. Identify what was accepted, by whom and when. Verifying a simulated receipt signed with a test key does not establish real third-party receipt or time. 3. Identity is separate from permission

Authentication

Checking evidence for a claimed identity or attribute. Authenticating an API account through a token, for example, does not establish that its user approved an individual payment.

Authorization

Whether the actor has permission for the particular operation. Reading a record may be permitted while deleting it is not. Compare the actual action with delegation, target, expiry and revocation. A valid signature or successful login does not by itself grant that permission.

Terminology reference: RFC 4949 — security terminology (Informational; author interpretations). This Informational RFC includes its author's interpretations; neither it nor this glossary establishes a new authentication method or permission model for VSO products. Continue with the AI agent security guide.

4. Defining what counts as the whole set

These explanations help readers understand the declared-scope research proposal. They add no new requirement to the current specification.

Declared scope

The stated systems, period, operations, exclusions and observation boundaries for an evaluation. Example: payment requests in test environment A during one morning. Declaring that boundary does not prove every action within it was observed.

Expected set

The evidence obligations derived from agreed sources and rules. Defining it as only what arrived cannot establish what is absent. An execution-side closure record, for example, may support checking which requests need outcome records.

Fulfillment / completeness

Whether the agreed evidence requirements are met, separate from signature integrity. An evidenced missing required outcome can establish non-fulfillment. Insufficient grounds for the expected set or observation boundary prevent a favorable conclusion about the whole set.

Definitions and boundaries: Declared scope and advance commitment — unadopted discussion draft. Preserve the draft's status and baseline. See choosing an evidence verifier and VAP's limits.

5. Explain why evidence was not delivered

Withheld, unavailable and missing

Record reasons for non-delivery separately. Withheld identifies intentional non-disclosure; unavailable records inability to obtain material; missing identifies a required item absent from the delivered set. A claimed reason alone establishes neither permitted non-disclosure nor confirmed omission.

No delivery receipt for a notification does not establish that the notification was never sent. Record the evidence, applicable policy and unresolved question. Proposed disposition handling: Declared scope and advance commitment — unadopted discussion draft. For practical intake records, see receiving photos and proofs.

6. Read failures, errors and unknowns separately

These are reading distinctions, not shared output-code definitions for every verifier. Check the exact tool revision and command contract for names, exit codes and aggregation rules.

FAIL / requirement not met

A label may indicate that an applied check did not meet its requirement, such as a mismatch between an original file and the expected hash. Retain the failed check. That alone is not a finding of deliberate tampering or fraud.

ERROR / processing problem

Check whether input format, reading failures or dependencies prevented the required evaluation. This is different from concluding that evidence was forged. Preserve the original and diagnostic information; investigate rather than counting an error as success.

Unknown, unassessed or unverified

Evidence may be insufficient, outside scope or unsupported. These reasons differ: record an unknown key separately from an unimplemented check. A signature match with an unknown expected count does not establish fulfillment of the whole set.

The declared-scope verifier's verify command can return exit 0 with a negative or indeterminate report. The interoperability demo has a different result contract. Read named result axes rather than transferring codes between tools. Declared-scope research verifier — modes, results and limits / Experimental interoperability demo — local contract and release boundaries. VeraSnap colors and checks have their own result guide.

7. Versions and the scope of a successful check

Fixed distribution and main

A fixed distribution is a retained published artifact such as a ZIP. main is a development branch that moves forward. A fix on main does not automatically enter an existing ZIP. Record the artifact digest, full source commit and release separately, even for the same product name. Preserve corrections and subsequent runs alongside historical records. Versions, distributions and known issues

Local PASS / successful test

A limited result for selected inputs, trust settings and rules. Rejecting a modified synthetic input as expected makes the test successful; it does not make that evidence pass. Do not extend the result to full conformance, production safety or capture of all real-world activity.

8. Who ran it, and who controlled the environment?

First-party CI

Automated checks prepared or controlled by the developer. The commit, environment, scope, skips and failures are part of the evidence. A successful GitHub Actions run does not establish a fresh run by an evaluator independent of the implementer.

Independent third-party reproduction

Assess a separate evaluator's fresh execution together with involvement in implementation or fixes, funding or contracts, environment control and assistance. Reading saved logs or having VSO run the steps is different from an independent fresh execution. Permission to publish results, a person's name and an organization name also requires separate confirmation.

The distinction between saved-evidence rechecks, fresh runs and assisted execution is illustrated in Fixed research kit — preservation, first-party evidence and reproduction status. Keep the machine output's independence: not_assessed unchanged; record the independence assessment and assistance separately.

Experimental extensions and proposed repairs remain unadopted; independent third-party reproduction has not been established. This glossary changes no normative requirement, existing implementation, signed data, fixed distribution or K3 condition. Historical test records and the distinction between first-party CI and independent reproduction remain intact.
