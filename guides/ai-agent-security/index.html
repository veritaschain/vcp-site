AI agent security: control permissions and inspect the evidence

Controlling what an AI agent can do and verifying what happened are separate tasks. Review one operation across authority, approval, tools and outcomes before expanding the scope.

Start with three trust boundaries

AI agent security covers external inputs, tool access, credentials and destination APIs as well as model output. Signing a log does not by itself prevent an inappropriate action.

  1. Input: treat instructions in retrieved pages, documents and tool responses as untrusted content, not user approval.
  2. Execution: check the operation, target and authority at the tool or receiving service. A prompt is not an access-control boundary.
  3. Evidence: distinguish what was observed, submitted or unavailable. A valid signature does not establish capture of every action.

What to check in an MCP connection

MCP connects tools; connection alone does not establish their safety. Consult the official MCP security guidance, version 2025-11-25, for the transport and authorization model you deploy.

  • Validate token audience; do not accept tokens issued for a different service.
  • Do not substitute a session ID for authentication. Authorization-enabled servers verify inbound requests.
  • Request minimal scopes and check per-client consent for proxy flows.
  • Treat local servers as executable code; restrict process, filesystem and network access.

This guide does not claim MCP implementation support or certification for a VSO product.

Example: an unknown CRM update outcome

This is a synthetic illustration, not an executed test result. An agent proposes an address update to a customer record; a reviewer approves the target and new value.

  1. Persist a pre-action record linking actor, approval, target and arguments.
  2. If the agreed failure policy requires it, do not send when that record cannot be persisted. First agree which business operation may be stopped.
  3. If the response is lost after sending, retain an unknown outcome rather than asserting success or failure.
  4. Reconcile with the destination's status or acceptance record. Link any retry to the original attempt and confirm the API's deduplication conditions.

Designing this flow does not prove that operations outside the gate are blocked. See the AI agent audit log guide for record-level examples.

Prepare an evaluation checklist

  • Name the operation, systems, time window, excluded paths and environment owner.
  • Describe credential and permission scope without submitting secret keys or token values.
  • Identify approval, request, acceptance, outcome and retry separately.
  • Test recording failure, denial, timeout and direct API calls in an authorized mock environment.
  • Report cryptographic integrity separately from scope sufficiency, including failed and unknown checks.
  • Record assistance, executor, environment differences and publication permissions separately.

Minimize sensitive prompts, personal data and credentials in both logs and support requests. Decide which fields to retain, where references point, who may read them and how long they are kept.

Status and limitations

This explanatory guide adds no normative requirements or product guarantees. Experimental extensions remain unadopted; independent third-party reproduction has not been established. First-party CI and synthetic tests are distinct from an independent fresh execution or production suitability.
