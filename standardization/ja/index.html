セクション 1

現在地の正直なステータス

VeritasChain Protocol (VCP) は、IETF RFC を強く意識して設計されています。VSO は現在 5 件の個人 Internet-Draft（draft-kamimura-vap-framework-02、draft-kamimura-scitt-vcp-05、draft-kamimura-rats-behavioral-evidence-02、draft-kamimura-scitt-refusal-events-04、draft-vso-cpp-core-04）を公開していますが、いずれも IETF ワーキンググループに採択されておらず、IETF における地位はありません。

本ページでは、VCP がどのような技術的前提に立っており、将来的にどのような標準化経路を想定しているかを説明します。

なぜこれが重要か

標準化ステータスについて透明性を保つことは、VCPのコア哲学と一致しています：マーケティング上の主張ではなく、暗号学的に検証可能な記録。私たちは、時期尚早な発表ではなく、技術的なメリットと運用実績によって信頼性を獲得することを信じています。

セクション 2

既存 RFC との技術的整合性

VCP は以下の IETF RFC と互換性のある形で設計されています。これにより、Internet-Draft の作成や、他の RFC ベースシステムとの相互運用性を支えています。

RFC 8785

JSON Canonicalization Scheme (JCS)

決定論的なJSONシリアライゼーションにより、すべての実装で暗号ハッシュ用の同一バイトシーケンスを保証。

RFC 6962

Certificate Transparency

CTパターンに準拠したMerkle Tree監査設計により、効率的な包含証明と改ざん検出を実現。

RFC 9562

UUIDv7

タイムスタンプ埋め込み、ソート可能、グローバルにユニークな識別子をイベントIDとして使用。

RFC 8032

Ed25519 署名

エドワーズ曲線デジタル署名により、高セキュリティ、優れたパフォーマンス、コンパクトな署名を実現。将来のPQCサポートも想定。

RFC 3339

タイムスタンプ

ISO 8601互換の日時フォーマットにより、システム間で一貫したタイムスタンプ表現を実現。

FIPS 180-4

SHA-256

NIST承認のセキュアハッシュアルゴリズムをすべてのハッシュチェーンとMerkle Tree操作に使用。

この整合性は、Internet-Draft の作成と他の RFC ベースシステムとの相互運用性を支えています。

セクション 3

IETF RFC までの想定ロードマップ

IETF RFC 化は、短期的な目標ではなく中長期の選択肢として位置づけています。まずは VCP v1.x を実運用で成熟させた上で、次のステップを検討します。

1

実装と運用実績の蓄積

現在のフェーズ

デプロイメント経験の蓄積を進めています。現状：外部実装はゼロ、いかなる手続においても受理されたEvidence Packはゼロです。営業実績の訂正・補足（2026年10月24日）：従来の契約件数は原資料との照合が未了のため、数値の訴求を取り下げています。契約がゼロという判断ではありません。 訂正の詳細

  • Early Adopter Program からのフィードバック収集
  • VC-Certified Silver / Gold の運用実績
  • VCP Explorer APIはモックデータを返し、2026-10-08時点でビルドは失敗していました。SDKはインターフェース仕様のみです。
2

コミュニティ・ドラフト版の公開

完了

vcp-spec をベースに、IETF Internet-Draft テンプレートに沿った草案を個人 Internet-Draft として公開し、コミュニティレビューを受けています。

現行: draft-kamimura-scitt-vcp-05（個人提出）
3

関連 IETF コミュニティとの対話

予定

関連する IETF ワーキンググループとの対話、および潜在的な BoF (Birds of a Feather) セッションへの参加。

潜在的な WG

SCITT, RATS (Security Area)

代替経路

適切な WG がなければ BoF セッション → 新 WG 形成

4

Internet-Draft 提出

個人提出済み

datatracker.ietf.org に個人 Internet-Draft を提出済みで、現在 5 件が有効です。個人提出は IETF における地位を意味しません。

5

WG 採用 & RFC 化プロセス

目標

WG 採用が決まった場合：WG 内での改訂、running code 実績の継続、IETF Last Call → IESG レビュー → RFC 化。

IETF は「ラフコンセンサスと動くコード」の原則で運営 — デプロイメント実績が不可欠です。
セクション 4

関係者の関わり方

VCP の標準化プロセスは、実装者と利用者からのフィードバックに強く依存します。

Early Adopter Program や VC-Certified の参加企業は、VSO の個人 Internet-Draft の今後の改訂内容に対して、実装フィードバックを通じて実質的な影響力を持つことになります。

標準に「従う」だけでなく、「設計に参加する」立場になれることが、VCP エコシステムの大きな特徴です。

実装者

実装フィードバックが仕様改善に直接反映されます

VC-Certified 企業

認証取得企業はVSOのドラフトに実装フィードバックを提供可能

規制当局

規制の観点からのインプットで初日から規制上の期待との整合を図ります
